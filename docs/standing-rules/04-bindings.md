# 4. Привязки skills и tools

Эта стадия выполнена после [инвентаризации](01-inventory.md), [вывода поведения](02-desired-behavior.md) и [контрактов](03-contracts.md). Все 73 объявленных skills и 116 tools имеют конкретную привязку. Машиночитаемая версия — [capabilities.json](capabilities.json).

## Как применять таблицы

Это discovery-снимок среды на 2026-10-22, а не обещание установленной сейчас возможности и не инструкция вызвать весь каталог. До действия проверяются текущие exact names/schema; выбранный skill полностью читается. Часть исходных skill descriptions обрезана хостом: они не устанавливают недостающие steps, права, модель или параметры.

Шаги: **S1** — цель/полномочия/коррекции; **S2** — источники/skills/schema; **S3** — модель/прогноз/контракты; **S4** — действие и наблюдаемая проверка; **S5** — независимый review; **S6** — полное завершение/память/отчёт. Полное определение шагов находится в предыдущей стадии.

- **Обязательно**: выполнить при истинном условии, применимости и действующих полномочиях. Для общей операции выбрать один достаточный доступный инструмент; все альтернативы вызывать не нужно. Названный обязательный механизм нельзя объявить проверенным по успеху другого.
- **Желательно**: полезный маршрут, который можно заменить достаточным разрешённым способом. Если пользователь явно назвал skill либо его актуальный trigger точно сработал, загрузка обязательна даже у строки «желательно». После выбора workflow его прочитанные инструкции соблюдаются полностью.
- **Основание** различается: «контракт» — требуемая операция/свидетельство; «trigger» — объявленное условие discovery, которое проверяется перед загрузкой; «выбранный workflow» — обязанность внутри уже выбранного процесса; «опциональный маршрут» — самостоятельного gate нет.
- Полномочия задаются исходным поручением и текущими инструкциями. Инструмент публикации, отправки, настройки среды или записи не получает разрешение от присутствия в этой таблице. Уже данное применимое разрешение сохраняется.
- Важный outcome проверяется после последней затронувшей его правки. Результат tool нужно прочитать; admission, pending receipt, screenshot без осмотра и зелёный lint не означают закрытый outcome.

## Согласование специальных случаев

Native mcode task в наблюдаемой версии принимает agent_name, description, prompt и run_in_background; все launches выполняются с run_in_background=true. Используется exact installed role/requestRef, при конфликте имён — agent:<stable-name>. Старые упоминания Agent/subagent_type и моделей в descriptions не становятся API или настройкой. Model/effort задаются лишь по действующей schema и разрешённому override. Для task-cycle нельзя подменить точную роль названием в prompt.

Владелец поставки организует implementation-critic в фоне и вне task-skill; внутри task-cycle используется его предусмотренная проверка. Каждый критик получает исходную задачу в общем виде и нейтральные locators; защищающие реализацию аргументы и предыдущие verdicts не передаются. Leaf reviewer не запускает review самого себя. Недоступность native роли остаётся явно непроверенным gate даже при полезном ad-hoc audit.

Старое описание layout-audit рекламирует три viewport. Действующий контракт77 задаёт пять CSS widths: 360, 390, 768, 1024, 1440, а также проверку между точками, около затронутых breakpoint и при меняющем geometry содержимом. Framework-specific defaults не отменяют это требование. Desktop frame size и CSS viewport не равны автоматически.

Graph инструменты помогают находить зависимости; решающий source всё равно читается. При использовании codebase-memory graph обязательны его актуальные coverage/freshness процедуры для cited/operated-on paths и negative claims. Недоступный индекс не блокирует bounded direct-source поиск, когда конкретный graph mechanism не является требуемым объектом проверки.

Control-task сохраняет полную долговечную постановку: при material change нужен set **или** patch. Agent-state сохраняет новое проверенное reusable knowledge до возможной compaction и не хранит текущий progress. Host get_goal/update_goal управляет существующим host lifecycle и не заменяет эти хранилища. Confirm/checkpoint — optional compatibility; storage failure не останавливает разрешённую работу.
